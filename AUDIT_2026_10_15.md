## Preserved behavior

Configuration defaults, AI routing, content generation/validation, chart variations, universe discovery, approval/policy gates, publishing hours, gap/hourly/daily caps and configured 25-image cap are not loosened. Planning preserves allocation decisions. Three-day cleanup and seven-day exact duplicate/report histories remain; receipts, command fingerprints, protected work and uncertain submissions are retained. No automatic blind retry of a Binance publication was added.

HTTP liveness stays separate from operational readiness so a rolling deployment can become healthy before the old worker releases its exclusive lease. Fast status identifies itself as memory observations and cannot authorize publishing. Full reports and mutations still use database checks.

The independent poller keeps private administrator authorization and bounded rates. It keeps uncompleted mutation offsets unacknowledged, deduplicates actions on the operational path and stops when another writer is observed. It never renews journal ownership from the status thread. If ownership observation fails, only read-only observations are offered; no new mutation is forwarded or update offset acknowledged. Explicit polling mode can reconcile an old webhook without dropping pending updates, consistent with the [Telegram Bot API](https://core.telegram.org/bots/api#deletewebhook).

## Verification and limits

See [VALIDATION.md](VALIDATION.md) for the final full-suite result. Tests cover provider takeover before publication, lost journal acknowledgement after a successful mocked Binance POST, exactly one POST across recovery, source-offline checkpoint restore, hashes/counts, partial repair rollback and staging cleanup, responsive Telegram while the worker thread is deliberately blocked, mutation ordering/ownership, stale readiness, no-op planning and concurrent shutdown.

PostgreSQL connection/transaction/cursor behavior uses driver protocol fakes; replication/publication faults use local SQLite-backed adapters and mocked HTTP. Real cloud RLS, network/firewall/TLS, role permissions, poolers, quotas, account status and real Binance/Telegram responses are not verified. No PostgreSQL server was available for integration testing. Actual catch-up time, host memory and monthly transfer require live measurements; no numeric performance guarantee is implied.

If Turso is unavailable or no PostgreSQL provider is verified current, publishing holds. Three PostgreSQL accounts share a mandatory journal/coordinator and are not four independent writers. A lost external response can require manual reconciliation; skipping uncertainty would create duplicate posts.

[Render Free instances](https://render.com/docs/free) can sleep after 15 minutes without inbound traffic, restart and hit quotas. Database repair cannot provide an always-on scheduler on sleeping compute or guarantee zero errors. This release preserves schedule rules and improves recovery/observability; it does not change cloud plans, billing, monitoring or production data.
