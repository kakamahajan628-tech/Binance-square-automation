# Exact chart recovery and guarded maintenance v22

Revision: `2026-10-26-exact-chart-recovery-22`. Based on complete v21.

## Suggestions implemented

Missing automatic chart PNGs can now be regenerated from the exact durable
pinned snapshot, saved metrics and saved presentation context. New chart creation
prefers the durable snapshot to a later RAM fetch of the same candle. If an older
or local draft has only its matching RAM evidence, that evidence is pinned once
before rendering. Normal production drafts already pin their evidence at creation.
The small image_recipe stores a snapshot reference/digest, metrics, context and
Pillow version; it never stores PNG bytes or another full candle snapshot.

On missing PNG, the regular automatic publisher's adapter invokes recovery using
the existing ONE chart executor and render lock. Work uses a temporary directory.
Only work completed inside the existing render deadline can reach the approved
artifact directory. Snapshot identity/digest, source, symbol, quote and interval
must match. Evidence must remain within the existing draft_max_age before AND
after rendering. The resulting PNG must match the approved SHA-256 and filename
exactly. Saving uses the existing atomic PNG writer. No new candles, AI request,
text rewrite, approval change, budget reservation or image cap increase occurs.
Old drafts without a recipe can recover from their saved event/context only if
the resulting bytes still match. A mismatch never replaces the approved hash.

The upload ticket/processing checkpoint is retained; rebuilding a local file is
not permission for a second PUT or content POST. Existing publication guards
still recheck stop/lease/freshness/approval before content submission. Uncertain
content submissions remain unreplayed. Missing evidence, expired evidence,
busy renderer, timeout or mismatched bytes route only the affected draft to
review, with no silent text-only fallback. Campaign graphics and manual photos/
memes are not candle charts and are not regenerated by this path. Their exact
files still need backup/restoration or a new authorized manual post.

Pillow is pinned to 13.0.0, including current JPEG/native-image security fixes.
The previous local build was 12.3.0. All five fixed aligned chart fixtures produced
identical RGB pixels AND identical PNG SHA-256 values in both versions locally
(FreeType 2.14.3, zlib 1.3.1.zlib-ng). Golden RGB hashes for each view are tested
with Pillow 13.0.0; they are independent of PNG compression packing. An exact
Pillow pin alone cannot guarantee all OS/native-library builds produce identical
bytes. The production approved-PNG SHA-256 check is always authoritative; a
different build producing different bytes requires review instead of substitution.
No live Render/Linux recovery has been claimed from these local comparisons.
Official release notes: https://pillow.readthedocs.io/en/stable/releasenotes/13.0.0.html

## Legacy image cleanup is explicit and offline

The new scripts/square_media_cleanup.py command is never imported or run by the
posting loop. It requires a verified full application backup from a current
provider and a stopped worker. Run outside posting hours or during a separately
chosen maintenance window; it is not safe to run concurrent maintenance against
the active bot. Preparing this release does not perform any live purge.

1. Save/inspect the existing full application export outside Render. It contains
   private image bytes; protect it. Verify the source provider is at the journal
   head before treating it as the final recovery backup. Preserve Turso as well.
2. Stop the old application worker and disable auto-deploy for maintenance.
3. Use the SAME existing private process ENV/cluster settings and run:

   python scripts/square_media_cleanup.py plan --backup saved-backups/verified.jsonl.gz

4. Review the count. To apply the explicit one-time removal:

   python scripts/square_media_cleanup.py apply --backup saved-backups/verified.jsonl.gz --confirm PURGE_BACKED_UP_LEGACY_MEDIA

The whole backup footer/checksums are validated before writes. Each eligible
legacy payload must match its exported row exactly. The PNG/hash/filename are
validated. Active pending/review/in-flight/uncertain image references are skipped.
Apply takes a normal exclusive worker lease and rechecks it plus the row and
protected references per transaction. It replaces only backed-up png_base64 media
payloads with hash/size/disk metadata; no post text, receipt, budget or history is
deleted. A later failure stops remaining work; already committed rows are safe
because their exact bytes are in the verified backup. Rerunning is idempotent.
Database controls are never cleared and ownership is never forced.

Old journal entries/checkpoints cannot be edited or deleted individually: that
would break the verified hash chain. Their existing normal checkpoint/compaction
flow remains unchanged. Storage reclamation is not necessarily immediate; old
replicas/backups/journal prefixes and PostgreSQL dead tuples follow their normal
retention/compaction. Do not reset Turso or force replica promotion for cleanup.

## Suggestions checked and intentionally left unchanged

Webhook/polling modes are already mutually exclusive in application startup.
DESK_TELEGRAM_POLLING=false starts neither poller; Telegram.poll also checks this
flag, while the webhook endpoint rejects polling mode. A webhook secret alone
does not configure Telegram's remote webhook URL. Existing explicit polling-mode
conflict handling is retained. No mode switch or extra getWebhookInfo loop was
added. Official API: https://core.telegram.org/bots/api#getting-updates

Heartbeat stays at 30 seconds. The worker lease is 120 seconds, but the separate
Turso writer lease is 60 seconds, with a conservative LOCAL deadline of 45 seconds.
Changing the only periodic renewal to 45-60 seconds would remove that safety
margin and risk idle writer expiry or avoidable command/failover stalls. No lease
TTL, fencing, promotion, publication schedule or standby behavior was changed.

## Preserved behavior and files

AI writers/prompts/provider order, content validation/quality, scheduler cadence,
automatic target/hourly cap/gap/hours, manual extra 10/day, chart dimensions and
quality, render timeout, database failover and retention are unchanged. Healthy
publishing does not run maintenance. The recovery path adds bounded CPU/disk work
and a saved-snapshot database read only when needed; it is not literally zero cost.
PNG bytes remain disk-only, with no new DB/base64/journal/replica image copy.
