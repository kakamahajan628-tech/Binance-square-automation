# Verified secondary repair and HTTP responsiveness

The live report showed Aiven ready at the journal head, while Neon and Supabase both failed entry 33819, statement 1: an `entities` UPDATE expected one row and matched zero. This can mean a missing row or a different status/predicate. It does not identify the correct old row by itself. The accompanying monitor-down report had no exact timeout/status or path, so its cause has not been confirmed in Render.

Upload the complete release ZIP into the existing Git repository and redeploy the existing service. Keep the current database, Turso, schedule, image and AI ENV settings. Alternatively replace app.py, database_failover.py, replica_batch.py and turso_journal.py, and add worker_runtime.py and replica_entity_repair.py, all inside square_desk/. No new packages are needed.

The service now uses one separate operational event-loop thread for its existing scheduler, heartbeat, Telegram, HTTP clients and background image lifecycle. HTTP control commands are sent to that same operational loop, preventing shared async-client use across loops. Database-heavy authenticated GET routes run in FastAPI's normal thread pool. The public GET/HEAD `/health` route still performs no database/network checks and can respond while the worker or a status query is blocked by synchronous database work. Its meaning is HTTP liveness, not confirmation that posting or databases are healthy. Authenticated `/health/details` and `/publish_status` retain actual operational checks. Posting windows, gaps, caps, scan cadence, three-day cleanup and the configured 25-image cap are unchanged; service.py, scheduler.py, publisher.py and config.py are byte-identical to v7.

For an affected secondary, automatic repair is narrowly limited to statement 1 of a point UPDATE with expected=1, actual=0. It requires an authorized fresh-start baseline and complete journal history from sequence 1 to the target checkpoint. The hash chain and every entity mutation's row count are checked while reconstructing a bounded canonical entity table. Only a known SQL subset is supported. The failed UPDATE must match the reconstructed preimage. No row is invented from a current Aiven copy or an unsupported/incomplete history.

Before changing the secondary, its metadata, secondary role and cancellation state are rechecked under the PostgreSQL transaction/advisory lock. The old row, or its absence, and the proven preimage are archived and read-back verified in owner-controlled square_replica_entity_archive. A single row is restored and verified. The replica watermark is unchanged. Normal strict replay then retries the original entry and catches up. No application mutation callback or external publication POST is replayed, and no automatic failback was added. Existing audit-only repair remains separate.

Proof is bounded to 100,000 sequences, 64 MB of encoded history, a 32 MB in-memory SQLite canonical table, 2 MB for the repaired row and approximately 120 seconds checked between entries/network calls. Reads use at most 256 entries and 2 MB combined encoded payload per request, allowing an existing oversized first entry alone. One proven row is cached for another replica at exactly the same checkpoint. The existing one replication thread performs the proof; it adds no repair thread. There are at most four successful entity repairs per node per process. This may require a one-time journal download, not a cloud bandwidth guarantee.

Missing/corrupt/trimmed history, unsupported SQL, an unproven primary UPDATE, unique conflicts, archive failure, changed checkpoints or insufficient permissions hold repair. Deterministic verification failures are marked verification_failed and retry_paused_until_restart, rather than re-running the same failed entry every minute. Restart re-probes; it does not itself fix inconsistent rows. Transient database connection failures retain the existing cooldown. Never force sequence numbers or skip the failed entry.
