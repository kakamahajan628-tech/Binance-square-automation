# Posting and replica repair v9

This release addresses the reported state: Aiven is current, Neon and Supabase fail the entities UPDATE at sequence 33819, and v8 cannot prove the missing preimage (`entity_canonical_missing`). The current-source rebuild replaces that stalled historical reconstruction. It adopts the current fenced Aiven state as a new verified checkpoint; it does not claim that the missing historical INSERT was recovered.

## Deploy into the existing service

1. Use the complete ZIP for the whole repository, or open `Posting-Replica-Repair-v9-files/square_desk` and copy **all its Python files** into the repository's existing `square_desk` directory. Existing filenames replace their counterparts; new files are added there. Do not put them inside `square_desk/square_desk`.
2. Commit the files together. In the existing Render service choose **Manual Deploy > Deploy latest commit** if automatic deployment has not already started. Keep the existing build/start commands and ENV/secret files. No new dependency or ENV key is required.
3. When startup completes, send `/status`, then `/publish_status`. The revision must be `2026-10-14-snapshot-posting-repair-9`. This identifier names the repair generation, even when deployed on 15 October.

The active provider remains Aiven while it is healthy. Rebuild starts in the existing single background replica thread. A secondary can show `snapshot_rebuilding`, then `snapshot_rebuild.status=restored_verified_checkpoint`, then `catching_up` or `ready`. Both backups are current only when each reports **ready, pending_entries=0, applied_sequence=journal_sequence** in the same report. A transient small pending count can appear as normal new writes arrive. A `held` reason or provider connection/quota failure requires examination; a deploy alone is not confirmation of cloud readiness.

The old global rejection is not cleared, no draft is force-approved and no uncertain submission is reposted. The original report says publication is globally unblocked. Use `/status full`, `/ai_status`, `/errors` and `/queue` if the queue remains empty; unavailable AI or rejected/stale drafts can still prevent content from qualifying. Posting remains subject to the existing local publishing hours.

## What the repair changes

A separate read-only repeatable-read PostgreSQL transaction exports a consistent snapshot of entities, state, audit and budgets plus the source sequence/hash. It does not take the live writer's advisory lock. Counts, ordered row hashes, a compressed-file hash, the cluster/baseline and the authoritative journal anchor must agree. The source migration gate must already be verified. Approved text/PNGs, receipts, controls, budgets, worker leases and pending/sending/uncertain states are copied exactly without backup-import normalization.

The compressed checkpoint is uploaded in bounded chunks into owner-fenced Turso tables, downloaded again and verified before it can be marked ready. It is private application data, not a downloadable dashboard artifact. The same durable checkpoint is reused for the second replica and after restart when eligible. Limits are 32 MB compressed per checkpoint, 128 MB raw row data, 4 MB per row and 100,000 rows. Total checkpoint compressed payload is capped at 64 MB (base64 storage adds overhead); reaching the cap holds repair rather than growing without bound. Incomplete checkpoints also count toward this cap. No original mutation journal entries are deleted to make a repair succeed.

Under the secondary's PostgreSQL transaction/advisory lock, all four original tables and replica metadata are first copied to owner-controlled `square_replica_rebuild_archive`. Archive counts must agree. The four application tables are then replaced from the verified checkpoint and read back for full ordered count/hash verification. An owner-controlled proof record is stored and the replica metadata advances to the checkpoint in that same transaction. Any failure rolls back the entire target replacement. Role, metadata, cancellation and server-side journal-owner/epoch fencing are rechecked. The source database is never cleared or restored. Strict journal replay then applies later mutations, rather than bypassing a bad entry in the old state. No external publication callback is replayed. No automatic failback is introduced.

Future accepted entities UPDATEs journal their complete returned row as an UPSERT, so a secondary receives the authoritative resulting state instead of requiring an absent preimage. The original conditional UPDATE, row count and claim outcome still execute once on the primary; a zero-row claim creates no journal mutation. The existing journal format and strict per-statement count checks remain in force.

The normal zero-batch worker now runs one scan task alongside its scheduler. Due eligible posts do not await a long market/AI scan. Scan cancellation is tied to lease loss and shutdown; the final publisher still checks ownership, freshness, approval, spacing, daily/hourly caps and duplicate/uncertainty gates. Saver mode retains its existing awaited scan lifecycle. `/status` uses two bounded application SELECTs, plus the existing authority/checkpoint queries, for a short report; `/status full`, `/dashboard`, `/publish_status` and `/ai_status` retain detailed diagnostics. Synchronous database/network calls can still take time on an unhealthy provider; this is not a universal latency guarantee.

Publishing configuration, scan settings, content checks/prompts, five chart layouts, the configured **25-image daily cap**, AI attempt policy and three-day cleaner are preserved. Rebuilding requires a one-time data transfer and extra archive/checkpoint storage. Local tests do not establish real provider throughput, Render memory use, cloud access permissions, continuous uptime or monthly bandwidth below 5 GB.

## Local verification

The packaged regression suite covers the reported missing-row path, exact receipt/control preservation, both replicas rebuilt without changing the active provider, MVCC export while the writer advances, durable checkpoint reuse, archive/restore/readback corruption, cancellation, source/target-role changes, fence loss, lost commit acknowledgements and new complete-row replication. PostgreSQL adapter tests check isolation ordering, bounded server cursors, server-side archival and rejected archive counts. Posting tests stall a scan while a ready mocked post and Telegram control succeed, then verify single-scan ownership, pause/stop/restriction/spacing gates and lease-loss cancellation.

Final full-suite result: **332 passed** on 15 October 2026. These use temporary local databases and mocked APIs. PostgreSQL syntax, ownership/RLS, advisory locks and real cloud permission/timeout behavior still need validation after deployment. No live credentials, database changes, deployment or Binance posts were used in local verification.

Implementation references: [PostgreSQL transaction characteristics and snapshot semantics](https://www.postgresql.org/docs/current/sql-set-transaction.html), [Psycopg server cursors](https://www.psycopg.org/psycopg3/docs/api/cursors.html#psycopg.ServerCursor).
